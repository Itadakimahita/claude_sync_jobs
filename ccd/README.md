# CCD — распределённый оркестратор агентов Claude Code

Одна задача на естественном языке → автоматическая декомпозиция → параллельная работа агентов
Claude Code на нескольких устройствах → слияние через git → финальная проверка.

Архитектура и обоснование решений: [../distributed-claude-code-orchestrator.md](../distributed-claude-code-orchestrator.md).
Этот файл — практическое руководство: как подключить устройства и пользоваться системой.

## 1. Как это работает

```
 вы: cli.py submit "…"
          │
          ▼
   ┌─────────────┐   план: подзадачи A, B, C      ┌────────────┐
   │ КООРДИНАТОР │ ─────────────────────────────► │ git remote │
   │  (1 штука)  │ ◄───── слияние веток ───────── │  (origin)  │
   └──────┬──────┘                                └─────▲──────┘
          │ воркеры сами опрашивают /claim              │ push ccd/<task>/<key>
   ┌──────┴───────┬──────────────┐                      │
   ▼              ▼              ▼                      │
 воркер 1      воркер 2       воркер 3  ────────────────┘
 (ноутбук)    (десктоп)       (сервер)
 claude -p     claude -p      claude -p
```

* **Координатор** — один процесс. Принимает задачи, просит Claude Code разбить задачу на подзадачи,
  хранит очередь в SQLite, сливает готовые ветки в интеграционную.
* **Воркер** — запускается на каждом устройстве. Сам забирает подзадачи у координатора (входящие
  порты открывать не нужно), запускает в git worktree `claude -p`, прогоняет тесты, пушит ветку.
* **Git remote** — единственный канал передачи кода между устройствами.

Важно понимать: модель работает на серверах Anthropic. Устройства дают агентам «руки» (файлы,
тесты, сборки). Параллельные агенты тратят квоту аккаунта примерно во столько же раз быстрее,
сколько их запущено.

## 2. Что понадобится

| Что | Где |
| --- | --- |
| Python 3.9+ | координатор и все воркеры |
| `git` | координатор и все воркеры |
| Claude Code (`claude`) с выполненным входом | координатор (планировщик) и все воркеры |
| Git remote, доступный всем машинам, с правом push в `ccd/*` | GitHub / GitLab / Gitea / bare-репозиторий |
| Сеть между координатором и воркерами | LAN или Tailscale / WireGuard |

### Авторизация Claude Code

CCD не управляет авторизацией — он вызывает обычный `claude`, поэтому работает всё, что работает у вас:

* **Подписка (в т.ч. Enterprise):** на каждой машине один раз запустите `claude` и войдите (`/login`, SSO).
* **API-ключ:** `export ANTHROPIC_API_KEY=...` в окружении процесса (координатор и воркер).
* **Bedrock / Vertex:** если Claude Code на машине уже настроен на них.

Проверка на каждой машине — должен отработать **без интерактивных вопросов**:

```bash
claude -p "ответь одним словом: ок" --output-format json
```

В JSON должны быть поля `result`, `is_error`, `total_cost_usd`. Если названия в вашей версии другие —
поправьте разбор ответа в `worker.py` (функция `execute`) и `server.py` (`extract_plan`).

> Перед автоматизацией на нескольких устройствах уточните условия вашего тарифа или договора
> (Enterprise) на параллельные автоматические запуски. Лимиты общие для аккаунта.

## 3. Установка

На **каждой** машине (координатор и воркеры):

```bash
git clone <ваш-репозиторий-с-ccd> ccd     # или скопируйте папку ccd/
cd ccd
python3 -m venv venv
./venv/bin/pip install -r requirements.txt
```

Дальше все команды выполняются из папки `ccd/`.

## 4. Git-репозиторий

Координатор клонирует ваш репозиторий, создаёт ветку `ccd/<id>/integration` и пушит в неё; воркеры
клонируют его и пушат ветки подзадач `ccd/<id>/<ключ>`. Значит **и координатору, и каждому воркеру**
нужен доступ к репозиторию с правом push (SSH-ключ или токен). Проверьте на каждой машине:

```bash
git ls-remote git@github.com:me/app.git          # чтение
```

Варианты remote:

* **GitHub/GitLab:** приватный репозиторий + SSH deploy-ключ с правом записи на каждой машине.
  Защитите `main` от прямых пушей — CCD пишет только в `ccd/*`.
* **Свой сервер без GitHub:**

  ```bash
  # на сервере
  git init --bare /srv/git/app.git
  # у вас, один раз залить код
  git remote add ccd ssh://user@server/srv/git/app.git && git push ccd main
  ```

  Адрес для CCD: `ssh://user@server/srv/git/app.git`.
* **Локальный тест на одной машине:** `git init --bare /tmp/app.git`, залейте туда `main` и
  используйте путь `/tmp/app.git` как `--repo`.

Ветка `--base` (по умолчанию `main`) должна существовать в remote.

## 5. Запуск координатора

Выберите одну машину (сервер, десктоп — любая, которая включена, пока идёт работа).

```bash
export CCD_TOKEN="$(openssl rand -hex 24)"     # общий секрет — сохраните его!
echo "$CCD_TOKEN"

# только эта машина:
./venv/bin/uvicorn server:app --host 127.0.0.1 --port 8787
# доступен другим устройствам (лучше — по Tailscale-адресу вместо 0.0.0.0):
./venv/bin/uvicorn server:app --host 0.0.0.0 --port 8787
```

Состояние (SQLite и клоны репозиториев) лежит в `./data` (меняется через `CCD_DATA`).
Проверка, что координатор жив:

```bash
curl -s -H "Authorization: Bearer $CCD_TOKEN" http://127.0.0.1:8787/workers
# → []
```

## 6. Подключение воркеров

На каждом устройстве, которое должно выполнять работу (включая ту же машину, где координатор).

**1. Создайте конфиг:**

```bash
cp worker.example.json worker.json
```

**2. Отредактируйте `worker.json`:**

```json
{
  "server": "http://100.64.0.1:8787",
  "token": "тот-же-секрет-что-у-координатора",
  "name": "laptop",
  "workdir": "~/.ccd",
  "slots": 2,
  "cpu_limit": 85,
  "poll_s": 5,
  "max_turns": 40,
  "timeout_s": 3600,
  "test_timeout_s": 1800,
  "permission_mode": "acceptEdits",
  "allowed_tools": "Read,Edit,Write,Grep,Glob,Bash(npm test:*),Bash(npm run:*),Bash(pytest:*),Bash(git diff:*),Bash(git status:*)"
}
```

Главное, что нужно поменять:

* `server` — адрес координатора, **доступный с этого устройства**.
* `token` — тот же `CCD_TOKEN`.
* `slots` — сколько агентов одновременно может работать на устройстве (начните с 1–2).
* `allowed_tools` — **добавьте команды ваших тестов и сборки**, иначе агент не сможет их запускать:
  `Bash(go test:*)`, `Bash(make test:*)`, `Bash(cargo test:*)` и т. п.

**3. Запустите:**

```bash
./venv/bin/python worker.py worker.json
# worker 3f9a1c2d зарегистрирован, слотов: 2
```

**4. Проверьте с любой машины:**

```bash
export CCD_SERVER=http://100.64.0.1:8787 CCD_TOKEN=<секрет>
./venv/bin/python cli.py workers
# 3f9a1c2d  laptop       слотов=2  online
# 7be04d11  desktop      слотов=4  online
```

Если воркер не появился — см. [«Частые проблемы»](#13-частые-проблемы).

## 7. Отправка задачи и наблюдение

```bash
export CCD_SERVER=http://100.64.0.1:8787
export CCD_TOKEN=<секрет>

./venv/bin/python cli.py submit \
    "Добавить авторизацию: backend на JWT, форма логина во фронтенде, документация API" \
    --repo git@github.com:me/app.git --base main --test "npm test"
# создана задача a1b2c3d4

./venv/bin/python cli.py watch a1b2c3d4
```

Параметры `submit`:

| Параметр | Назначение |
| --- | --- |
| `prompt` (первым аргументом) | что нужно сделать; чем конкретнее — тем лучше разбиение |
| `--repo` | URL репозитория (тот, что доступен координатору и воркерам) |
| `--base` | ветка, от которой отталкиваемся (по умолчанию `main`) |
| `--test` | команда проверки; выполняется **на воркере** после работы агента и в VERIFY |

Пример вывода `watch` (обновляется каждые 5 секунд):

```
Задача a1b2c3d4 [running]  стоимость ≈ $3.42
  ✅ A          merged     3f9a1c2d  Модуль авторизации (backend)
  🔄 B          running    7be04d11  UI формы логина
  ✅ C          merged     9a77e2f0  Документация API
```

Статусы подзадач:

| Значок | Статус | Значение |
| --- | --- | --- |
| ⏳ | `pending` | ждёт свободного воркера или своих зависимостей |
| 🔄 | `running` | выполняется на воркере |
| 📦 | `completed` | воркер запушил ветку, идёт слияние |
| ✅ | `merged` | слита в интеграционную ветку |
| ⚠️ | `conflict` | при слиянии возник конфликт, создана подзадача `<ключ>-fixN` |
| ❌ | `failed` | исчерпаны попытки или нефатальная ошибка |

Статусы задачи: `planning` → `running` → `done` | `failed`.

Остальные команды:

```bash
./venv/bin/python cli.py status a1b2c3d4   # один снимок без ожидания
./venv/bin/python cli.py tasks             # последние задачи
./venv/bin/python cli.py workers           # воркеры и их online/offline
```

### Как формулировать задачи

* Хорошо: «Добавить пагинацию в `/users` и `/orders`, обновить тесты» — части лежат в разных
  модулях и распараллеливаются.
* Плохо: «Переписать всё на новый фреймворк» — всё завязано на общие файлы, планировщик вернёт
  одну подзадачу, и параллелизма не будет.
* Указывайте критерии готовности и команду тестов (`--test`) — по ней агент и оркестратор понимают,
  что работа закончена.
* Для первого запуска возьмите небольшую задачу и маленький тестовый репозиторий.

## 8. Что происходит внутри

1. **Planning.** Координатор клонирует репозиторий, создаёт `ccd/<id>/integration` от `--base`,
   запускает Claude Code в режиме «только чтение» (`Read,Grep,Glob`) и получает JSON с подзадачами:
   ключ, заголовок, промпт, `owns` (какие файлы можно менять), `deps` (от каких подзадач зависит).
   План проверяется: уникальные ключи, существующие зависимости, нет циклов, у независимых подзадач
   `owns` не пересекаются. Невалидный план → задача `failed` с причиной.
2. **Scheduling.** Подзадача готова к выдаче, когда все её `deps` в статусе `merged`. Свободный воркер
   забирает её (`/claim`), если есть слот и загрузка CPU ниже `cpu_limit`.
3. **Execution (воркер).** Создаётся `git worktree` от свежей интеграционной ветки (поэтому зависимая
   подзадача видит код своих зависимостей) → запускается `claude -p` → проверяется, что изменены
   только файлы из `owns` → запускаются тесты (`--test`) → воркер коммитит и пушит ветку
   `ccd/<id>/<ключ>`. Сам агент `commit/push` не делает.
4. **Integration.** Координатор последовательно сливает ветку подзадачи в интеграционную (`--no-ff`).
5. **Конфликт.** Создаётся подзадача `<ключ>-fixN`: воркер сам начинает слияние интеграционной
   ветки, агент убирает маркеры конфликта, воркер проверяет, что маркеров не осталось, и коммитит.
6. **Verify.** Когда все рабочие подзадачи слиты, создаётся `VERIFY`: агент запускает тесты и вносит
   минимальные исправления, если что-то упало.
7. **Done.** `VERIFY` слита → задача `done`.

Повторы: ошибка подзадачи (тесты упали, агент вышел за `owns`, таймаут, воркер пропал) → она
возвращается в очередь, **до 3 попыток**, причина прошлой ошибки попадает в промпт следующей.
Если воркер перестал присылать heartbeat (выключили ноутбук), через ~90–120 секунд его подзадачи
возвращаются в очередь.

## 9. Забрать результат

Когда статус `done`, результат — ветка `ccd/<id>/integration` в вашем remote:

```bash
git fetch origin
git log --oneline --graph origin/ccd/a1b2c3d4/integration | head -20
git diff main...origin/ccd/a1b2c3d4/integration --stat

# GitHub CLI:
gh pr create --base main --head ccd/a1b2c3d4/integration \
   --title "Авторизация (CCD a1b2c3d4)" --body "Результат работы агентов CCD"
```

**Просмотрите изменения перед слиянием в `main`.** Если задача `failed`, ветка с частичным
результатом тоже остаётся в remote — её можно изучить или доработать вручную.

Уборка после работы (ветки `ccd/*` сами не удаляются):

```bash
git push origin --delete $(git ls-remote --heads origin 'ccd/a1b2c3d4/*' | awk '{sub("refs/heads/","",$2); print $2}')
```

## 10. Справочник

### Переменные окружения координатора

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `CCD_TOKEN` | — (обязательна) | общий секрет для API |
| `CCD_DATA` | `./data` | SQLite и клоны репозиториев |
| `CCD_PLAN_TIMEOUT` | `900` | таймаут планировщика, сек |
| `CCD_CLAUDE` | `claude` | исполняемый файл Claude Code для планировщика |

### Переменные окружения CLI

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `CCD_SERVER` | `http://127.0.0.1:8787` | адрес координатора |
| `CCD_TOKEN` | — (обязательна) | тот же секрет |

### Поля `worker.json`

| Поле | По умолчанию | Назначение |
| --- | --- | --- |
| `server`, `token` | — | адрес и секрет координатора (обязательны) |
| `workdir` | — | папка для клонов и worktree (обязательна), например `~/.ccd` |
| `slots` | — | число одновременных агентов (обязательно) |
| `name` | hostname | имя в `cli.py workers` |
| `cpu_limit` | `85` | не брать новые подзадачи при загрузке CPU выше, % |
| `poll_s` | `5` | пауза между опросами координатора, сек |
| `max_turns` | `40` | потолок числа ходов агента |
| `timeout_s` | `3600` | потолок времени работы агента над подзадачей |
| `test_timeout_s` | `1800` | потолок времени прогона тестов |
| `permission_mode` | `acceptEdits` | режим прав Claude Code |
| `allowed_tools` | см. пример | список разрешённых инструментов (allowlist команд) |
| `model` | по умолчанию Claude Code | модель для подзадач на этом воркере |
| `labels` | `[]` | зарезервировано: сейчас хранится, но планировщик их не использует |

### HTTP API координатора

Заголовок `Authorization: Bearer <CCD_TOKEN>`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/tasks` | `{prompt, repo, base, test_cmd}` → `{id}` |
| GET | `/tasks`, `/tasks/{id}` | список и состояние задачи с подзадачами |
| POST | `/workers/register`, `/workers/heartbeat` | регистрация воркера и heartbeat |
| GET | `/workers` | список воркеров |
| POST | `/claim` | воркер забирает подзадачу (`204`, если нет работы) |
| POST | `/subtasks/{id}/complete`, `/subtasks/{id}/fail` | результат подзадачи |

```
├── cli.py               # командная строка
├── worker.example.json  # пример конфига воркера

```

## 11. Автозапуск (systemd)

Координатор — `/etc/systemd/system/ccd-server.service`:

```ini
[Unit]
Description=CCD coordinator
After=network-online.target

[Service]
User=ccd
WorkingDirectory=/opt/ccd
Environment=CCD_TOKEN=замените-на-секрет
Environment=CCD_DATA=/var/lib/ccd
ExecStart=/opt/ccd/venv/bin/uvicorn server:app --host 100.64.0.1 --port 8787
Restart=always

[Install]
WantedBy=multi-user.target
```

Воркер — `~/.config/systemd/user/ccd-worker.service`:

```ini
[Unit]
Description=CCD worker
After=network-online.target

[Service]
ExecStart=%h/ccd/venv/bin/python %h/ccd/worker.py %h/ccd/worker.json
Restart=always

[Install]
WantedBy=default.target
```

```bash
systemctl --user enable --now ccd-worker
```

На macOS используйте `launchd` или просто запускайте воркер в `tmux`.
Не забудьте, что сервису нужны переменные для авторизации Claude Code (если используете
`ANTHROPIC_API_KEY`) и доступ к SSH-ключу для git.

## 12. Безопасность

Агент с правом выполнять команды на устройстве — это риск.

* **Не используйте `bypassPermissions`** на личных машинах. Держите `acceptEdits` и явный
  `allowed_tools`.
* **Изолируйте воркеры:** отдельный пользователь ОС или контейнер, `workdir` без доступа к личным данным.
  Не подключайте основной рабочий компьютер, пока не настроена изоляция.
* **Токен координатора** — длинный случайный; слушайте на приватном интерфейсе (Tailscale/WireGuard),
  в продакшене добавьте TLS. Сейчас токен один на всех и передаётся в открытом виде по HTTP.
* **Секреты** не должны лежать в репозитории: содержимое репо и зависимостей — недоверенный ввод
  (prompt injection).
* **Git-права:** ключ только на push в `ccd/*`, `main` защищён.
* **Ревью:** вливайте интеграционную ветку через PR с человеческим просмотром.

## 13. Частые проблемы

| Симптом | Причина и решение |
| --- | --- |
| `Задайте переменную окружения CCD_TOKEN` | не экспортирован токен в этом терминале |
| `координатор недоступен` | неверный `CCD_SERVER`, файрвол, координатор слушает только `127.0.0.1` |
| `HTTP 401 bad token` | токен воркера/CLI не совпадает с `CCD_TOKEN` координатора |
| Воркер не появляется в `workers` | проверьте `server` и `token` в `worker.json`, смотрите вывод воркера |
| Задача сразу `failed`, `planning: …` | координатор не смог клонировать репозиторий (нет прав / ветки `--base`), `claude` не вошёл в аккаунт, или план невалиден — текст причины в `status` |
| Подзадача падает: `claude вернул не-JSON` | `claude` просит вход или флаги не подходят вашей версии — запустите команду из раздела 2 вручную |
| `изменены файлы вне owns` | агент вышел за назначенные файлы; повторится до 3 раз, затем задача `failed`. Уточните формулировку задачи или расширьте разбиение |
| `тесты не прошли` | хвост лога тестов виден в `status`; проверьте, что тесты запускаются на воркере (зависимости установлены) |
| Агент не может запустить тесты | добавьте нужные команды в `allowed_tools` воркера |
| Подзадачи долго `pending` | нет online-воркеров со свободным слотом, высокая загрузка CPU (`cpu_limit`) или не слиты зависимости |
| Подзадача вернулась в `pending` сама | воркер потерял связь; её возьмёт другой (до 3 попыток) |

Логи: координатор и воркер пишут в свой терминал / journal (`journalctl --user -u ccd-worker`).
Данные координатора: `./data/ccd.db` (SQLite) и `./data/repos/<id>` (клоны).

## 14. Ограничения текущей версии

Это MVP — он нужен, чтобы проверить идею на 2–3 устройствах:

* нет команды отмены задачи и ручного retry; остановить можно только убив процессы;
* нет бюджета на задачу и паузы-backoff при упоре в лимиты (ошибка лимита считается обычной
  повторяемой ошибкой);
* `labels` воркеров пока не влияют на выдачу подзадач;
* после перезапуска воркер регистрируется заново, старая запись остаётся в списке как `offline`;
* один общий токен, без TLS;
* автоматического создания PR нет — только ветка `ccd/<id>/integration`;
* упавшую (`failed`) задачу перезапустить нельзя — отправьте новую.

Планы развития — в разделе 16 основного документа.
